# CLAUDE.md — MenuCart

Project brief for Claude Code. Read this first, then `docs/PRD.md` for full requirements and `wireframes/` for every screen.

## What we're building

MenuCart turns a home cook's weekly menu (breakfast, lunch, dinner × Mon–Sun, up to 21 dishes) into one merged, **halal-safe** grocery list. The user types dish names; the app works out the ingredients, flags non-halal ones with a swap, merges quantities, lets the user tick what they already have, and gives a one-handed shopping mode that works offline.

Primary user: Muslim home cook in Indonesia, shopping at supermarkets and traditional markets, on Android phones, sometimes on weak or no signal.

## Decisions already made

- **Platform:** installable web app (PWA) first, mobile-first at 390×844. Later shipped to Google Play as a Trusted Web Activity. No React Native for now.
- **Hosting:** Vercel.
- **Auth:** Clerk, passwordless. One email field for both sign up and sign in. The email contains a **magic link and a 6-digit code**; support both. No passwords, no social login in MVP.
- **Guest mode:** users can use the app without an account. Guest data is device-only and uploads to the account on sign-up.
- **Local-first:** every write goes to the device first (IndexedDB), then syncs. Only sign-in, AI ingredient generation for unknown dishes, and cross-device sync need the network.
- **Language:** English UI first, Bahasa Indonesia second. Each language is used on its own: in English every word is English (ingredient names included, no Bahasa second line), and vice versa. The only exception is the titip belanja WhatsApp message, which is always Indonesian.

## Suggested stack (confirm with the user before installing)

- Next.js (App Router) + TypeScript + Tailwind CSS
- `@clerk/nextjs` for auth (email link + email code strategies enabled in the Clerk dashboard)
- Postgres (Neon or Supabase free tier) with Drizzle ORM for server data
- IndexedDB via Dexie for local-first storage and a sync queue
- Service worker for offline (e.g. Serwist) with an app-shell cache
- AI ingredient generation through a server route (API key stays on the server). Results are cached in a shared dish library so each dish is generated once.

Check the current docs for Clerk, Next.js and any PWA library before wiring them up; APIs change.

## Region (as built, v2)

- City picker (P3) covers Jawa Tengah: 35 kota/kabupaten, 576 kecamatan, 8,563 desa/kelurahan, generated into `src/lib/region/` by `node scripts/region-data.mjs` from cahyadsn/wilayah (MIT, Kepmendagri 2025 codes). Villages and outlines load lazily.
- Kecamatan and desa map to their kota/kabupaten. "Use my location" reads GPS once and tests the simplified outlines on the device; coordinates are never stored or sent. Outside Jawa Tengah → the province average (`id: "33"`).

## Prices (as built, v2)

- `src/lib/prices/pasar.ts`: per ingredient, how recipe units convert (pcs, clove, tsp…), how the pasar sells it (kg in ¼ steps, ikat, ekor in ½, bungkus, botol…), whether it's bought loose by rupiah (chillies, bawang, rempah), and its price. About 110 ingredients; the rest show "Add price".
- Sources (`sources.ts`, tried in order): Badan Pangan Nasional monthly consumer prices for Jawa Tengah (`bapanas-jateng.ts`, generated by `node scripts/price-data.mjs [file.csv]`), then MenuCart estimates. Both ship with the app, so prices work offline. SP2KP city prices go first once allowed.
- `price.ts`: `quoteItem` (sellable amount + cost; loose rounds up to Rp1.000, min Rp2.000; others round to Rp500), `linePrice` (bought price → user price → estimate), `weekMoney` (spend = to buy + bought; at home and skipped don't count).
- `ListItem.userPrice` (the user's own price for this week) and `boughtPrice` (frozen when ticked bought) survive regeneration.
- Every list line is `ui/ItemRow.tsx` (pantry, By menu, By aisle, shopping `size="lg"`): checkbox, name, detail, and on the right the price, price + unit pill ("1/2 kg", English units in English), "Add price", or the amount (at home / no price). `rowRight` and `lineMoney` in `list/format.ts` pick it. Checkbox = at home in pantry and list, bought in shopping mode.
- By aisle groups by pasar stall (`lib/list/stalls.ts`: sayur & bumbu, ayam & telur, daging, ikan, tahu & tempe, kelontong, supermarket) with a subtotal each; shopping mode keeps the sections. Shared lines say "400 g needed: Capcay 200 g + Tahu tek 200 g".
- Tapping a list line (By aisle, By menu) opens `list/ItemSheet.tsx`: what to buy, which dishes use it, the price and its source, a note for whoever shops (`ListItem.note`), "Paid a different price?" and "Can't find?". Edit a price saves `userPrice` (this week only; "Reset to estimate" clears it) and checks prices over 3× or under ⅓ of the estimate (`checkPrice`), suggesting a zero-off typo fix. Lines without a price show "Add price". The list's budget card says where prices come from, the data month and what ≈ means. Shared anonymous prices aren't built, so the sheet doesn't mention sharing.
- Plan edits update the saved list in place (`refreshList` from the List screen, keeping ticks); a new non-halal dish waits for the halal review instead. Planner Generate and `refreshList` record what changed (meta `listChange`) for the "Plan changed · Rendang added" banner and "New" tags; the review's second pass doesn't.
- Over budget: red card with "Over budget · N cheaper swaps" (lines with a priced alternative ≥ Rp2.000 cheaper, `prices/cheaper.ts`). Item details then offer "Cheaper this week"; using one sets `replacedBy` and its price as `userPrice`. "Price jumped" (≥ 20% month-on-month in Bapanas) shares that sheet; it's quiet while no commodity moves that much.
- Freshness (`list/freshness.ts`): short-lived ingredients and how long they keep. By aisle says "Cook Tue · keeps 1–2 days"; the planner adds "spinach only keeps 1–2 days" (warning) or "uses tempe from Monday" to a dish's cost line. The week is assumed bought in one trip, today for this week.
- "Send to whoever shops" (`list/TitipSheet.tsx`, footer of both list views and the header share icon): a WhatsApp message built by `titipText` in `lib/list/share.ts`, always in Bahasa Indonesia, grouped by stall, sellable amounts, item notes, "Estimasi" and budget. Switches: rupiah for loose items (default on) and "Dibuat pakai MenuCart" (default off), remembered per phone in localStorage. "Send via WhatsApp" opens wa.me; "Copy text" has a fallback for browsers that block the clipboard API. Shopping mode (`/shop`, in the `(app)` group) has the tab bar like Plan and List.
- Settings mirrors onboarding: the compact EN/ID switch (`settings/LanguageSwitch.tsx`) beside the title, then `KitchenFields` (step 1) and `BudgetFields` (step 2), then account. An installed app reloads once when a new version's service worker takes over (`OfflineSupport`), so nobody keeps old screens.
- Weeks start on `Settings.weekStartsOn` (onboarding step 1 and Settings; Monday by default). Use `weekStartOf` / `dayIndex` from `lib/week.ts`, never assume Monday. Changing it runs `changeWeekStart` (`lib/weekstart.ts`): every planned meal keeps its date and moves into the week that date now falls in; the current list moves to the new current week and updates there.
- Countable ingredients (`piece` in `prices/pasar.ts`: eggs, chillies, shallots, garlic, onions, tomatoes, terong, timun…) can be bought "By weight" or "By piece" (`ListItem.buyBy`, toggled in item details and remembered per ingredient in meta `buyBy`). The dish editor converts amounts when switching between g and pcs (`prices/convert.ts`).
- Money on screen (`list/BudgetMeter.tsx`): the planner projects the week with `useWeekMoney` (plan merged as Generate would, keeping saved ticks); pantry and list use `weekMoney` on the saved list. Dish and meal-card costs are `dishCost` shares. Settings saved before v2 have no `weeklyBudget`: the list shows a one-time "Set your weekly budget" notice until settings are saved.

## Auth & first run (as built)

- Clerk switches on only when `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` is set (`src/lib/auth-config.ts`); without keys the app is guest-only and sign-in screens say so. See `.env.example`.
- Clerk dashboard: Email address required, **Email verification code** and **Email verification link** on for sign-up and sign-in, passwords off.
- One email field: `signIn.emailCode.sendCode`, falling back to `signUp.create` on `form_identifier_not_found` (`src/lib/signin.ts`). The code is primary; "Email me a sign-in link instead" sends a link. Clerk sends either a code or a link per email, not both in one (custom email templates need a paid plan).
- No `proxy.ts` yet: nothing reads auth on the server until sync (step 7). All routes stay static.
- First run: `/` Welcome → `/onboarding` → `/plan` (guests get a 3-dish sample week). Device flags live in the `meta` table (`onboarded`, `tipsSeen`, `signupSnooze`, `lastUser`).
- On sign-in, guest weeks get `ownerId` = the user's id; the actual upload comes with server sync.

## Offline (as built)

- Serwist (`@serwist/turbopack`): worker in `src/sw.ts`, served from `/serwist/sw.js` by `src/app/serwist/[path]/route.ts`. Registered only in production builds (`npm run build && npm start`), never in `next dev`.
- All screens are precached from `src/lib/precache-routes.ts`; a test fails if a new page isn't listed there.
- Offline shows a slim banner (`OfflineBanner`); nothing waits on Clerk, which can't load offline.

## Server: sync and AI (as built, step 7)

- Postgres on Supabase (transaction pooler, `DATABASE_URL`), Drizzle schema in `src/server/db/schema.ts`, migrations in `drizzle/` (`npm run db:generate`, `npm run db:migrate`). RLS is on for every table; only the app server (owner role) reads them.
- Sync: one generic `sync_rows` table (user, entity, key, jsonb data, deleted, device `updated_at`, global `version`). `POST /api/sync` upserts with last-write-wins and returns rows since the device's cursor. Client in `src/lib/sync/`; local deletes must call `recordDeletes()` inside the same transaction so the deletion syncs.
- AI: `POST /api/dishes/generate` → shared `dish_library` cache first, then Claude (`claude-opus-5-5`, structured JSON output, effort low, server-side fallback on refusals). Daily caps per account, per guest (hashed IP) and overall (`ai_usage`). Unknown dishes are saved with `aiStatus: "pending"` and filled by `src/lib/ai.ts` when online. Needs `ANTHROPIC_API_KEY`; without it, dishes fall back to manual ingredients. **Off in v1** (`AI_GENERATION_ENABLED = false` in `src/lib/ai-config.ts`, no API budget yet): unknown dishes are manual-only and the client never calls the route.
- Clerk runs as `src/proxy.ts` on `/api/*` only, so pages stay static and precached.

## Data model

Source of truth is `src/lib/types.ts`; this is a summary.

```ts
type Meal = 'breakfast' | 'lunch' | 'dinner';
type HalalStatus = 'halal' | 'non_halal' | 'check';
type Section = 'produce' | 'meat_poultry' | 'seafood' | 'dairy_eggs' | 'dry_goods_spices' | 'others';

interface Settings { householdSize: number; halalMode: boolean; autoSwap: boolean; meals: Meal[]; language: 'en' | 'id';
  weeklyBudget: number;  // whole rupiah, default 200.000
  city: { id: string; name: string; province: string };  // BPS code; 2 digits = province average
  weekStartsOn: number;  // Date.getDay() numbering, 1 = Monday (default)
}
// Money: formatRupiah() in src/lib/money.ts, always "Rp142.500" / "≈Rp6.000", never IDR.
interface Week { id: string; ownerId: string | null; startDate: string; /* first day of the week (Settings.weekStartsOn), ISO; id = startDate */ }
interface Slot { weekId: string; day: 0|1|2|3|4|5|6; meal: Meal; dishId?: string; dishName: string; more?: { dishId?: string; dishName: string }[]; isSample?: boolean; updatedAt: number; /* last edit per slot wins */ }
// A meal can hold several dishes: the first in dishId/dishName, the rest in `more`. Always read them with slotDishes() (src/lib/plan.ts).
interface Dish { id: string; name: string; aliases: string[]; source: 'library' | 'ai' | 'user'; cuisine?: string; meals?: Meal[]; servings: number; ingredients: Ingredient[];
  customized?: boolean;            // an edited library dish, saved on device; overrides the library copy
  swaps?: Record<string, string>;  // original ingredient key → swap option id, or 'keep'
}
interface Ingredient { key: string; name: string; localName?: string; qty: number; unit: string; section: Section; halal: HalalStatus; swappedFrom?: string; }
// Halal swaps (src/lib/dishes/swaps.ts): ranked options per non-halal key. A line's qty is ratio × the original
// unless fixed; no lines = leave it out. Effective ingredients = dish.ingredients with dish.swaps applied.
interface SwapRule { forKey: string; role: string; options: { id: string; note: string; lines: { key: string; ratio?: number; qty?: number; unit?: string }[] }[]; }

interface Amount { qty: number; unit: string; }
// One line per ingredient key per week. Ingredient fields are a snapshot so the list renders offline
// without the dish library. Several amounts = incompatible units shown as sub-lines.
interface ListItem {
  weekId: string; key: string; name: string; localName?: string; section: Section; halal: HalalStatus;
  amounts: Amount[];
  uses: { dishId: string; dishName: string; count: number; amounts?: Amount[] }[];   // count > 1 when planned twice (×2); amounts = that dish's share
  state: 'to_buy' | 'at_home' | 'bought' | 'skipped';
  swappedFrom?: string;       // line comes from a halal swap for this original
  replacedBy?: string;
  noLongerNeeded?: boolean;   // bought, then its dish was removed from the plan
  userPrice?: number;         // what the user paid/pays, this week only
  boughtPrice?: number;       // price when ticked bought
  updatedAt: number;
}
```

The grocery list is a saved snapshot: "Generate" merges the week's dishes (all 7 days) and reconciles with the saved list by ingredient key, so ticks survive. The list view groups it by menu (one card per planned meal) or by aisle; ticks are shared per ingredient.

Ownerless (`ownerId: null`) weeks are guest data.

## Rules that must hold

- Never block the user on the network. Offline = slim banner, never a modal.
- Never lock a user out of their list when a session expires; ask to sign in only to sync.
- Halal status is always **icon + text**, never colour alone.
- Swaps are suggestions, not rulings; show the one-time disclaimer on the first swap.
- "Check" items (cheese, gelatin, stock cubes) get a note, never an automatic swap.
- Tap targets ≥ 44 px; text respects system font size.
- Merging: same ingredient key + compatible unit → sum; incompatible units → sub-lines.
- Ticks survive list regeneration.
- At most one sign-up prompt per session for guests; "Not now" hides prompts for 3 days.

## Suggested build order

1. Project setup, tokens, app shell, bottom tab bar (Plan / List / Shop).
2. Local data layer (Dexie) + planner with breakfast/lunch/dinner slots, using a hard-coded dish library of ~20 dishes. No auth yet.
3. Ingredient merge + grocery list + pantry check + shopping mode, all from local data.
4. Halal tags, swap table and the review screen.
5. Offline: service worker, offline banner, queued generation.
6. Clerk auth (magic link + code), guest mode, guest-to-account upload.
7. Server sync (Postgres) and AI generation for unknown dishes with a shared cache.
8. PWA install, then Trusted Web Activity for Google Play.

Ask before adding dependencies beyond this list, and keep each step shippable.
